# AAC v1 — plan (draft for the owner)

Decided 2026-10-21 (owner: "a major change to the whole workings; so far it has mostly been retrofits";
then "no branch, just scrap what doesn't fit and reuse what can be used"). v1 is built directly on `main`;
the last v0 is the tag `v0.50.1-last-v0` (a fix for the running v0, if ever needed, comes from there). The
owner's HA keeps running v0 0.50.1 until v1 can do everything used daily; then one import brings the data
over and we switch (with a backup). `scripts/deploy_ha.sh` refuses a 1.x version unless `AAC_ALLOW_V1=1`.

The target is [streams.md → Target model](streams.md): everything is nodes with typed ports and wires;
the model request is a structured record that runs through a chain of nodes; groups hide the detail.

## What the core is

Only what every graph needs:

| Part | What it does |
|---|---|
| **graph** | node types (from modules), node instances per domain, typed ports, wires (stored; defaults by type and order until the owner changes one), annotating chains, groups, privacy and owner-only rules |
| **request record** | `model.request`: text, history, own words, `system` parts, `context`, `tools`, tier, where the answer goes back to |
| **model node** | picks a model from the pool by tier, runs **its own tool loop** (no longer HA's conversation machinery), records the run, writes `model.answer`; the queue (priority, due, critical, keep, coalesce) is its job |
| **pool and compute** | machines, models, roles, traits, rules (carried over from v0) |
| **runs** | every model call recorded with its steps (carried over) |
| **panel shell** | navigation, the node view, generic node settings from manifests, skins |
| **HA adapter** | the conversation entity (Assist uses AAC), calendar entity, sensors: thin, they write `model.request` / read the answer |

Everything else is a node type from a module.

## Node types vs. node instances

New in v1: a module brings node **types** (with ports, settings, kind); a domain's graph holds **instances**
of them, each with its own settings. So a domain can have two model nodes ("assistant" and "research"), or
two charters in two groups. The default graph of a new domain comes from a template (the group
"Assistant": chat → charter → memory → home → lists → calendar → plans → model → chat, plus the audio
pipeline and the automatic sources).

## Tools without HA's LLM API

v0 used HA's `llm.API` / chat log to merge tools and build the system prompt. v1 has its own small tool
protocol (name, description, JSON schema, call, read_only/destructive flags) and tool nodes add their tool
sets to `request.tools`. The model node offers them all or as a menu (v0's menu mode, carried over). HA's
own Assist tools (timers, HA to-do lists, live states) become an optional node "Home Assistant tools" that
wraps HA's API, so nothing is lost.

## Stored data (new layout, imported from v0 once)

```
aac.config: models, pool, traits, audio, languages, skins, queue settings,
            domains: {id: {name, graph: {nodes: {id: {type, settings, on}}, wires: [...], groups: [...],
                                         view: {containers}}}}
module storage and files: unchanged where possible (lists, triggers, voices, memory.db)
```
The import reads v0's `aac.config` (+ module storage) and builds each domain's graph from the template with
its v0 settings (charter text, agent prompt, module switches and settings, triggers, entity access).

## Phases

Status: phase 1, first step built (2026-10-21): `request.py` (the record, `async_prepare` runs the chain),
`model_node.py` (AAC's own tool loop, v0's behaviour carried over; HA's tool registry still merges the tool
sets), `core_nodes.py` (agent, home, setup, and "chat" as the sources), the charter, memory (recall + keeper)
and every module's tool set as annotating nodes, `conversation.py` a thin Assist adapter,
`broker.async_run_request` = chain → model node → `model.answer` on the bus. Not yet: node types vs.
instances, stored wires, the new data layout.
Built since: stored wires (1.0.0-dev.2) and node types vs. instances, first for the model (1.0.0-dev.10:
`Node.make` + `settings_schema`, a domain's added instances in `node_view.<domain>.instances`,
`aac/nodes/instances`; the model node wired at the end of the request chain answers, an added one with its
own tier and instructions; added instances are wired by hand).

1. **Skeleton:** graph (types, instances, wires, chains, groups as data), request record, model node with
   its own tool loop, Chat node, pool/provider/runs carried over. Tests. A chat works end to end.
2. **Tool and context nodes:** home (with entity access), memory (recall, keeper, tools), lists, calendar,
   plans, setup, charter, agent prompt, HA tools; menu mode.
3. **Sources:** heartbeat, triggers, HA Assist adapter, audio pipeline, wake word, companion, speaker.
4. **Panel:** the node view becomes the editor (add/remove nodes, wire, groups, node settings in place),
   chats, runs, compute. The UI redesign (docs/plans.md) fits here.
5. **Import and switch:** v0 → v1 import, a parity checklist with the owner, backup, switch on the real HA.
